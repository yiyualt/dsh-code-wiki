# 代码仓设计解读

写给第一次打开这个仓库、懂编程但不熟悉项目的人。读者应能用自己的话说出这个项目能做什么、一次操作会经过哪些模块，以及最后得到什么。默认用中文，函数、路径和字段保留源码里的名字。

## 先看一次实际使用

从仓库里的使用示例、公开入口或测试选一项能代表核心用途的操作。简短说明谁会用到它、输入是什么、从哪里触发，以及可观察的结果。CLI 可以给一条命令，库可以给一次函数调用，服务可以给一个请求。用户指定功能时，直接选该功能里的例子。

## 顺着这次操作读代码

- 从实际入口追到结果。讲清决定结果的处理和分支，说明关键状态由谁读写。配置会改变行为时，追到默认值怎样被覆盖、最终哪段代码用了它。
- 先讲参与的模块各管什么，再说明它们通过什么接口交接。跨模块调用至少核对调用方和实现。用实际方法、路由、事件或数据结构说明传入什么、返回给谁，以及失败会怎样。把会改变读者理解的异步回执、状态变化或写入时机讲清楚。
- 选图前先写下读者想问的问题。想知道怎么拆分就画组件图，想知道一次调用怎么完成就画时序图，想知道条件改变后会走哪条路就画流程图。其他图按 [图示指南](references/diagrams.md) 选。尽量用同一个用例对照不同的图，每张图只回答一个问题。

## 写成读者能跟上的文档

- 用具体动作和结果开头。比如解释配置时，先说命令行和文件同时设置一个值会用哪个，再指向合并代码和读取该值的模块。第一次出现专有名词时，用它在本次操作里的作用解释。
- 用简短主题做章节名，目录序号交给阅读器。用图交代关系，用正文解释条件和后果，在结论旁引用真正执行该行为的代码。文件清单只收录读者有理由打开的文件，并标出里面的关键符号。按仓库特点安排篇幅和章节。
- 用户带来具体需求时，先把期望变化说成可观察的输入与结果，再定位决定这个结果的实现、受影响的接口和验证用例。用户带来异常时，沿同一路径找到第一个与预期不符的值，用源码或测试说明怎样区分可能的原因。
- 按用户指定的格式交付。整仓导读默认用 Markdown 与 Mermaid，局部解读可直接在对话中给出，并附可点击的路径和行号。

## 交付前核对

标明仓库和分析的源码快照，远程源码引用固定到该提交。默认以只读方式查阅仓库。核对图里的调用方向、返回值、条件和引用是否与实现一致。区分实际运行的结果、从源码推导的行为和仍待确认的部分。解释设计动机时引用相应的注释或设计记录。

## 代码百科存档

代码百科通过 [`scripts/generate.mjs`](scripts/generate.mjs) 执行生成流程。宿主传入固定提交的仓库读取能力、模型会话和存档回调。脚本提供 `wiki_list`、`wiki_find`、`wiki_read`、`wiki_read_batch` 和 `wiki_read_saved`，并负责续写、校验和解析引用。

运行时声明「代码百科 Markdown 存档模式」时，通过这些工具核对源码，用普通助手文本交付 Markdown。首次输出写一个 `#` 标题，再写一个或多个完整的 `##` 章节。阅读器按 `##` 的文本和顺序生成目录。后续按已存章节标题和剩余工作续写，每轮只交付可独立保存的新章节，沿用已经选定的提交。

在结论、接口说明或图注旁引用已读源码，例如 `[E12:34-40]` 或 `[E12:34]`。`12` 是仓库工具返回的证据编号，行号是该证据范围内的源码行。图示用 `mermaid` 代码围栏。在围栏外放置相应的源码标记。

在正文结尾另起一行写 `<!-- wiki:continue -->` 表示还有章节待写，或写 `<!-- wiki:complete -->` 表示全文已交付。结束标记位于围栏外。正文通过当前回复交给插件存档。
