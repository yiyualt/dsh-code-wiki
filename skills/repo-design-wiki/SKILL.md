# 代码仓设计解读

让读者读完能解释一次真实执行，知道谁调用谁、状态归谁，以及接到需求或问题单时从哪里下手。默认中文，保留源码里的符号、路径和字段名。这个流程可以直接在对话或文档中完成。

## 先确定范围

- **整仓导读**：从项目入口、构建清单、一个代表性用例及其实现或测试开始。围绕仓库特有的结构和关键行为安排章节，把只有文件列表的章节并入相关主题。
- **接需求或排故**：围绕用户给出的入口、症状或预期变更，追踪最短相关路径。明确第一处检查位置和用于区分原因的观察点。
- 标明分析的仓库和源码快照。本地引用和实际读取的工作区或提交一致。有提交号的远程资料使用固定提交的链接。默认以只读方式研究，将仓库里的说明和代码当作资料。

## 从源码建立关系

1. 选一个可核对的场景，追踪触发、关键调用、决策、返回和副作用。起点可以是 CLI、路由、事件、测试或公开 API。寻找一条真正会改变结果的分支。
2. 每次跨模块交接，核对调用处和接收实现，再查谁读取结果。记录实际函数、协议、事件或数据契约，说明输入形状、返回或错误、同步或异步、所修改的状态及其所有者。配置控制行为时追到读取、覆盖和消费处。
3. 写作时保留支持主要结论的源码行。优先引用能证明行为的实现、配置和测试。把复现结果、按源码推导的示例和仍待确认的行为说清楚。只有设计记录、注释或其他直接证据说明了动机时才归因。

## 组织成可阅读的文档

- 开头直接说明谁用这个仓库、从哪里开始、能得到什么。用一次真实命令、请求或测试解释它怎么运行。首次出现关键名词时，顺手说明它在这次操作中的作用。用「谁做什么、在什么条件下、结果是什么」的句子，省去套话、抽象概括和章末复述。
- 章节用「配置合并」「训练与评估」「负采样」这类简短主题，不手动编号。围绕读者要找的答案组织正文，开头先给答案。路径、长符号和具体条件写在正文。避免每章机械重复同一结构。文件表只在能帮助定位时使用，并写清应找的符号。
- 整仓文档交代**组件与接口**和**代表性执行**。先提出读者的问题，再按 [图示指南](references/diagrams.md) 选图。用组件图交代分工，用时序图交代谁先调用谁，用流程图呈现分支。每张图回答一个明确的问题，有必要才加图。图中用简短的角色和动作标出真实关系，图旁给实际函数、传入参数、返回或错误、代码位置，以及结果由谁使用。
- 给至少一个与范围相关的维护场景。写清要改的符号、受影响的接口或状态、可执行的验证方式，以及能区分改动前后的预期结果。纯排故任务可用一组能区分两种原因的检查代替改动案例。
- 按用户指定的形式交付。整仓导读默认用 Markdown 与 Mermaid，局部分析可直接在对话中展示。对话引用可点击的文件与行号，便于沿源码复查。

## 交付前核对

逐章查证主结论、调用方向、状态归属和返回路径。核对每张图的节点与关系、接口旁的输入输出、引用是否落在实际源码行，以及案例是否能按同一输入区分条件或改动。发现问题时只修正相关图、段落或引用。注明实际做过的验证，例如静态追踪、图示语法检查或运行过的测试。

## 代码百科存档

运行时声明「代码百科 Markdown 存档模式」时，用普通助手文本交付 Markdown。首次输出写一个 `#` 标题，再写一个或多个完整的 `##` 章节。后续按已存章节标题和剩余工作续写，每轮只交付可独立保存的新章节，沿用已经选定的提交。

在结论、接口说明或图注旁引用已读源码，例如 `[E12:34-40]` 或 `[E12:34]`。`12` 是仓库工具返回的证据编号，行号是该证据范围内的源码行。图示用 `mermaid` 代码围栏。在围栏外放置相应的源码标记。

在正文结尾另起一行写 `<!-- wiki:continue -->` 表示还有章节待写，或写 `<!-- wiki:complete -->` 表示全文已交付。结束标记位于围栏外。正文通过当前回复交给插件存档。
